What the machine does

  • Read the instruction at the address in rip.
  • Do it.
  • Add its length to rip, and go again.

That loop is the whole computer.

Fetch, execute, step. A few billion times a second, and it has never done anything else. rip is the instruction pointer. It is the only register you cannot name in an instruction: nothing writes rip directly. A jump writes it, a call writes it, and returning writes it back. That is the list. Say the word memory here: one flat array of bytes, addressed from 0 up. There are no types in it. A byte is a byte, and what it means is decided by the instruction that reads it.

Sixteen registers

raxaccumulator, and the return valuer8argument 5
rbxnothing, todayr9argument 6
rcxcounts and shift amountsr10no history at all
rdxthe other half of a multiplyr11no history at all
rsisource, for the copy instructionsr12no history at all
rdidestination, for those same onesr13no history at all
rbpframe pointer, by habit onlyr14no history at all
rspthe machine stack pointerr15no history at all

Only rsp has a job the hardware insists on.

Sixteen places to hold a 64-bit value, and reaching one costs nothing. Reaching memory costs a lot more. That is the whole reason registers exist. The left column is old. Every name there is a duty some CPU had in the 1970s and that we are still living with. rbx is the honest one: it was the base register for 16-bit addressing, that job is gone, and it is now a plain register. The right column is new, added with 64-bit mode in 2003, which is why nothing on that side has a story. Only rsp is real. push, pop, call and ret all read and write it, and the kernel writes a signal frame through it. You cannot opt out of it. rbp is convention: nothing in the hardware cares, but a debugger walking a backtrace does. Most of the lab's functions need only a handful of these: the arguments arrive in rdi and rsi, and the answer leaves in rax.

Why one register has four names

19788086, 16 bits: ax, and ah/al as its two halves
198580386, 32 bits: eax, the E for extended
2003AMD64, 64 bits: rax, and r8 to r15 as well

rax, eax, ax and al are one register.
They name 64, 32, 16 and 8 bits of it.

Each generation kept the one before it running, so each name is still there. Nothing is copied or converted: write al and you have changed the bottom byte of rax, and reading rax afterwards shows it. The accumulator of a 1972 calculator chip, the 8008, is still bits 0 to 7 of rax on the machine in front of you. The lab's uppercase exercise, A6, reads a character into eax and writes it back from al. Two names, one register.

The rule that bites


mov     rax, -1         ; rax = 0xFFFFFFFFFFFFFFFF
mov     eax, 10         ; rax = 0x000000000000000A  - top half zeroed
mov     al, 10          ; rax = 0xFFFFFFFFFFFFFF0A  - top 56 bits kept

Writing a 32-bit name clears the upper 32 bits.
The smaller names do not.

This is the one surprise in the naming, and it is not a quirk to work around. It is a tool. mov eax, 10 and mov rax, 10 leave the same value in rax, and the 32-bit form is two bytes shorter, so that is what you write when the value fits. You will see "xor eax, eax" in the lab's solutions where the intention is to clear the whole of rax, and now you know why that is enough.

Reading a line


mov     rax, rbx        ; destination, then source
add     rax, 8          ; rax = rax + 8
mov     qword [x], 0    ; size, when nothing implies it

One instruction, one line. The comment is half of it.

Destination on the left. This is Intel syntax, which is what NASM speaks and what the lab is written in. If you have read AT&T syntax before, with the percent signs and the operands the other way round, forget it for today. An instruction carries its size in the operands. Two registers, and the register names say it. A register and a number, same. But "mov [x], 0" says nothing about how many bytes to write, so NASM makes you say qword, which is eight of them. byte, word, dword, qword: one, two, four, eight. Word means 16 bits here, forever, because it meant 16 bits on the 8086. A dword is a double word and a qword a quad word. The lab's strlen, A4, needs the smallest: cmp byte [rdi + rax], 0.

Square brackets mean memory


mov     rax, rbx                ; the value in rbx
mov     rax, [rbx]              ; the eight bytes rbx points at
mov     rax, [rbx + 8]          ; the cell one past that
mov     rax, [rbx + rcx*8]      ; cell number rcx
lea     rax, [rbx + 8]          ; that address, without reading it
movmove a value
leawork out an address and keep the address
Brackets are the only way to reach memory, and they read as "the contents of". This is the most useful slide in the deck: half of reading assembly is knowing whether a line touches memory or not. The fourth line is an array. A base address, plus an index times the size of one element: 1, 2, 4 or 8. The CPU does that sum inside the instruction. The lab's A5 sums an array of longs with exactly that line. lea is the odd one. It uses the same bracket syntax but never reads anything - it does the arithmetic inside the brackets and hands back the answer. It is the address calculator, borrowed as a general adder.

Arithmetic


add     rax, rbx        ; rax = rax + rbx
sub     rax, rbx        ; rax = rax - rbx
imul    rax, rbx        ; rax = rax * rbx, signed
cqo                     ; sign-extend rax through rdx:rax
idiv    rbx             ; quotient in rax, remainder in rdx

Two operands, and the left one is also the answer.

The first three read the same way: do it, and put the answer back in the left operand. The left operand is destroyed. If you want to keep it, copy it first. Division is the awkward one, and it is awkward for a reason from 1978. idiv takes one operand, the divisor, and it divides a 128-bit value held across rdx and rax by it. So rdx has to be set up first, and cqo is the instruction that does it: it copies the sign bit of rax through the whole of rdx. Forget cqo and a negative number divides into nonsense.

Bits


and     rax, rbx        ; bits set in both
or      rax, rbx        ; bits set in either
xor     rax, rbx        ; bits set in one, not both
xor     eax, eax        ; therefore: rax = 0

No bit differs from itself.

The first three are the ordinary ones and need no explanation beyond the line. The fourth is an idiom you have to be able to read, because it is everywhere and it looks like a trick. Anything exclusive-ORed with itself is zero. It is shorter than "mov eax, 0", and the CPU has recognised it as "clear this register" for thirty years. Read it as: rax is now zero. Not as: something clever happened.

Flags


cmp     rax, rbx        ; subtract, and keep only the flags
test    rax, rax        ; AND it with itself: zero flag set if zero

Neither one writes a register.
They leave a verdict behind.

There is a register nobody names: rflags. Almost every arithmetic instruction writes it as a side effect - was the answer zero, was it negative, did it carry. cmp and test exist to write those flags and nothing else. cmp does a subtraction and throws the difference away. test does an AND and throws that away. What survives is the verdict, and the next instruction reads it. test rax, rax is the second idiom of the day, and it means "is rax zero". ANDing a value with itself gives the value back, so the only thing it really settles is whether every bit was zero.

Jumps


jmp     done            ; always
jz      done            ; if the last result was zero
jnz     done            ; if it was not
jl      done            ; if less than, signed

A label is just a name for an address.

A jump writes rip. That is all a jump is. The conditional ones read the flags that cmp or test left. Notice the split: one instruction decides, a second one jumps. They are always written as a pair, and they do not have to be next to each other - anything in between that writes the flags will break it. jz and je are the same instruction with two names, because "the result was zero" and "the two were equal" are the same question after a cmp. Use whichever reads better at the line. jl is signed, and there is a separate jb for unsigned. Getting that wrong is a real bug, not a style choice, and the lab's A2 has test cases that catch it.

The machine stack


push    rax             ; rsp -= 8, then write rax there
pop     rax             ; read it back, then rsp += 8
call    puts            ; push the return address, then jump
ret                     ; pop it into rip

It grows downwards, and call uses it.

Four instructions, and they are two pairs. push and pop move rsp and touch memory. call and ret are push and pop with the return address as the value. Downwards is the thing to say out loud. Pushing makes rsp smaller. It is an accident of 1970s memory layout that everybody still lives with. This is also where the room should hear the word return: call remembers where to come back to by writing it in memory. That is what makes recursion work, and the lab's B4 is a factorial that calls itself: every call it makes is one more return address on this stack.

Who has to save what

caller-savedrax rdi rsi rdx rcx r8 r9 r10 r11
callee-savedrbx rbp rsp r12 r13 r14 r15

Arguments go in rdi, rsi, rdx, rcx, r8, r9.
The answer comes back in rax.

This is the System V ABI, the agreement every C function on Linux keeps. It is not a hardware rule. It is a promise, and libc keeps it. Top row: a function you call may destroy these. Want the value after the call, save it yourself. Bottom row: a function you call must hand these back untouched. This slide is the contract for every exercise in the lab. The test is C, and it calls your function this way: the arguments are already in rdi and rsi when your first instruction runs, and the test reads the answer out of rax after your ret. B3 is the bottom row as an exercise: a running total and a count that have to survive a call, kept in rbx and r12, which you must give back as you found them. One more rule, and it bites silently: rsp must be a multiple of 16 at the moment you execute a call. Get it wrong and printf can work for a long time and then crash for no visible reason. Tier B's notes page explains it, and its tests check rsp at every call.

What NASM adds


        section .text           ; code
        section .rodata         ; constants

msg:    db      "hello", 0      ; bytes
count:  dq      0               ; one 64-bit cell
SIZE    equ     65536           ; a name for a number, no memory

        global  max             ; let the test find max

Directions to the assembler.
Not instructions to the CPU.

Sections say what kind of thing follows, and the linker keeps each kind together. .text is code, .rodata is constants, .data is variables the program writes. db and dq lay bytes down where they stand: one byte at a time, or eight. A label in front is a name for that address. equ is different and worth a sentence. It reserves nothing. It is a name for a number, resolved while the file is being assembled. A label is private to its file unless it is declared global. Every exercise file in the lab starts with one of these lines, and it is how the C test finds your function.

The same program, twice

hello-syscall.asm


msg:    db      "Hello from a syscall", 10
msglen  equ     $ - msg

_start:
        mov     eax, 1
        mov     edi, 1
        mov     rsi, msg
        mov     edx, msglen
        syscall

        mov     eax, 60
        xor     edi, edi
        syscall

hello-libc.asm


msg:    db      "Hello from libc", 0


main:
        sub     rsp, 8
        mov     rdi, msg
        call    puts


        xor     eax, eax
        add     rsp, 8
        ret
Two ways to print a line: ask the kernel, or ask the C library to ask the kernel. Both files are in slides/examples/, both build, and both print a line. Say that before showing them - the room should know these are not slide snippets. Left: no libc at all. The kernel starts the program at _start, and nothing runs before it. Number 1 is write, number 60 is exit. It has to end itself, because there is nowhere to return to. Right: libc's startup code runs first and calls main, so returning from main is enough. puts finds the end of the string by looking for the zero byte, which is why the left one carries a length and the right one does not. The left one also writes its own newline; puts adds one. The sub rsp, 8 is the 16-byte alignment rule from two slides back. The right-hand column is the lab's B1, nearly line for line. There is a smaller file still, exit-syscall.asm, which is three instructions and no output. Mention it if anyone asks what the smallest program is.

Two conventions

syscallnumber in rax, then rdi rsi rdx r10 r8 r9
calladdress in the call, then rdi rsi rdx rcx r8 r9

Argument four moves,
because syscall destroys rcx itself.

Nearly the same, and the two marked registers are the whole difference. The syscall instruction writes its own return address into rcx and the flags into r11. Two registers destroyed by the act of making the call, so neither can carry an argument in, and argument four goes to r10 instead. Not taste, and not a kernel whim. Today is the bottom row. Every exercise in the lab is a function that a C test calls, and the ones that print go through puts or printf. No exercise makes a syscall, so the System V convention is the only one you need to hold in your head this morning.

What ./check does


nasm -f elf64 -g max.asm -o max.o
clang -no-pie test.c max.o -o test
./test

Assemble, link with the test, run it.

Three steps, and the lab does all three for you. nasm turns your one text file into one object file. clang compiles the exercise's test, which is C, and hands both to the linker, which resolves puts and printf against libc and writes the program. Then the test runs and says what it got. elf64 is the object format Linux uses, and -g records which line of your file each instruction came from, so gdb can show your source while it steps. The real command lines are in lab/tools/build.sh, with a few more flags and a comment on each. -no-pie is the one flag that matters if you ever build outside the lab. It is what lets "mov rdi, msg" and "call puts" be written as they are on the last slides. Without it the link fails with "relocation R_X86_64_PC32 ... can not be used when making a PIE object". The fix is -no-pie on the link line, not rewriting the call. DEMO, if the room is awake, in your own codespace: ./check a2. A function that is not written yet fails some cases and passes others by luck, and the output says which.

Bonus: one instruction, three jobs

x86-64


add     [rax], rbx

arm64


ldr     x2, [x0]
add     x2, x2, x1
str     x2, [x0]

Read the cell, add to it, write it back.

Both files are in slides/examples/, and the x86 one runs: it prints "cell = 40" and then "cell = 42". This is what CISC means, in one line. An x86 instruction may name a register and a memory address, and do the arithmetic between them. Three memory operations in one instruction: read, add, write. arm64 is a load/store architecture and does not allow it. Arithmetic happens between registers, and memory is reached only by a load or a store. So the same work is named in three instructions, and the machine you are holding is the one that needs three. Neither is better. The RISC argument is that three simple instructions pipeline better than one complicated one, and it largely won. The x86 one is shorter to read, which is what today is about.

Forth's +

Forth keeps its numbers on a stack in memory.


mov     rax, [DSP]              ; n2, the top item
add     DSP, 8                  ; drop it
add     [DSP], rax              ; and add it to the one underneath

The whole word, in three instructions.

Forth is a language with almost no syntax: "2 3 +" pushes 2, pushes 3, and + replaces the two with 5. Every number lives on a stack in memory, and DSP is a name for the register that points at the top of it. This is + out of src/words.asm, the Forth this repository is, unchanged. The third line is the instruction from the last slide, doing exactly the job it was made for: the answer belongs on the stack, in memory, so read it, add to it, and put it back without ever giving it a name. A Forth on arm64 writes this word with five instructions instead of three. That is the whole of the difference, and it is why a Forth and a CISC machine suit each other. Tier E of the lab builds a Forth like this one, word by word, until "2 3 + ." prints 5. Its notes page explains Forth from the start, so nobody needs to know any before they begin.

Optional: a loop in one instruction

x86-64


mov     rsi, source
mov     rdi, dest
mov     rcx, 1000
rep     movsb

arm64


mov     x2, #1000
copy:   ldrb    w3, [x0], #1
        strb    w3, [x1], #1
        sub     x2, x2, #1
        cbnz    x2, copy

The same copy. Only one of them needs a label.

Skip this slide if the clock says so. Nothing later needs it. movsb copies one byte from the address in rsi to the address in rdi and steps both pointers. rep says: do that rcx times, counting down. A whole copy loop, with its test and its branch, inside one instruction. This is the far end of CISC, and it is where those old register duties on slide 3 come from - source, destination, count, sitting in rsi, rdi and rcx exactly as the names say. On the right the loop is written out, because arm64 has no instruction like it. Read the last two lines as one sentence: take one off the count, and branch back to copy while the count is not zero. cbnz is compare-and-branch-on-non-zero, and it needs no flags. Both examples assemble; the arm64 one was built with clang on this laptop. No exercise needs rep movsb. It is here because when someone asks what CISC ever bought anybody, this is the answer, and on modern CPUs it is genuinely fast: the chip recognises the pattern and copies a cache line at a time.

One exercise


long max(long a, long b);
    

        global  max

        section .text
max:
        ; TODO: return the larger one
        mov     rax, rdi        ; return a for now
        ret

a is in rdi, b in rsi.
The answer goes in rax.

This is A2, nearly as the file arrives. The prototype is what the C test sees, and the System V slide is what turns it into registers. The file already assembles, links and runs. It is just wrong: it always returns a. So the test has something to say from the start, and the first thing to do with every exercise is to run it before changing anything. The TODO marks the line to change. While it is there, ./check calls the exercise "not started", so delete it when you start.

The loop


$ ./check a2
max(2, 3) ... expected 3, got 2
max(3, 2) ... ok
...
4 of 7 passed
./check a2build A2 and run its test
./debug a2the same, stopped at your first instruction

Every exercise is this loop. Run the test, read which cases fail, change the file, run it again. When the test and you disagree, ./debug runs the same test under gdb, stopped on the first instruction of your function, with the registers in a window at the top. Four commands get you through it: si runs one instruction, p $rax prints a register, c goes on to the next case, and q quits. Tier 0 walks through all of it. A crash is a result too: ./check names the case it was in and the signal that ended it, so a bad pointer does not look like a hang. An endless loop stops after five seconds.
